# Dify 1.16.1 Full Agent Architecture Design

## Goal

Upgrade the Azure Container Apps Terraform deployment from its current claimed Dify 1.15.0 baseline to Dify 1.16.1. Preserve classic Agent applications while adding the complete Dify Agent v2 runtime. Make the Agent v2 UI selectable through Terraform environment configuration without removing either runtime stack.

## Source Baseline

The project began from commit `7326784` of `nikawang/dify-azure-terraform` on 2024-07-01 and then evolved independently. It is not a generated translation of Dify's Docker Compose deployment, so version labels and image bumps are insufficient evidence of release parity.

The authoritative comparison sources are:

- Dify tags `1.15.0`, `1.16.0`, and `1.16.1`.
- `docker/docker-compose.yaml`, `docker/.env.example`, core-service environment examples, Nginx configuration, and Squid configuration at those tags.
- The official Dify 1.15.0, 1.16.0, and 1.16.1 release notes.

## Current 1.15.0 Audit

The current project includes the required classic core services:

- Nginx reverse proxy.
- API, worker, and singleton worker-beat containers using `langgenius/dify-api:1.15.0`.
- Web container using `langgenius/dify-web:1.15.0`.
- Classic code sandbox using `langgenius/dify-sandbox:0.2.15`.
- Plugin daemon using `langgenius/dify-plugin-daemon:0.6.3-local`.
- SSRF proxy, managed PostgreSQL, managed Redis, pgvector database, plugin database, Azure Blob storage, and persistent API/plugin shares.

The optional `api_websocket` Compose profile is intentionally absent because collaboration mode is disabled. Database migrations are enabled on API startup. The required 1.15.0 plugin auto-upgrade backfill is documented for existing installations and is unnecessary for a new empty database.

The audit found two material baseline gaps:

1. Nginx lacks the official `/openapi` route and WebSocket forwarding route present in Dify 1.15.0.
2. The mounted Squid configuration comes from the old Terraform lineage. It does not match Dify 1.15.0's private-network denial rules and must be replaced before calling the deployment 1.15-compatible.

The implementation will repair these gaps while upgrading to 1.16.1.

## Target Architecture

### Classic Agent Path

Classic Agent applications continue to use the existing API, worker, plugin daemon, classic code sandbox, PostgreSQL, Redis, storage, and Nginx components. Their resource names and data stores remain stable to avoid unnecessary replacement.

### Dify Agent v2 Path

The deployment adds all services required by the official Dify 1.16.1 Compose definition:

- `agentbackend`: `langgenius/dify-agent-backend:1.16.1`, internal port 5050.
- `localsandbox`: `langgenius/dify-agent-local-sandbox:1.16.1`, internal port 5004.
- `agentssrfproxy`: a dedicated Squid forward proxy with Dify 1.16.1 Agent ACLs, internal port 3128.

The API and worker call `agentbackend` with a generated bearer token. The Agent backend uses Redis database 2, the existing plugin daemon, the API inner endpoint, and `localsandbox`. The local sandbox receives HTTP and HTTPS proxy variables pointing to `agentssrfproxy` and uses generated shell-control authentication.

All three services are installed by default. `enable-dify-agent-v2` defaults to `true` and controls the web container's `NEXT_PUBLIC_ENABLE_AGENT_V2` value. Setting it to `false` selects the classic experience while leaving Agent v2 resources ready; setting it to `true` enables the new experience without reprovisioning data services.

### Azure Container Apps Network Limitation

Dify's Docker Compose deployment isolates `local_sandbox` with dedicated Docker bridge networks. Azure Container Apps in one managed environment does not provide equivalent per-application network policies. The design therefore applies the strongest controls available inside the existing architecture:

- All Agent service ingresses remain internal.
- `localsandbox` is configured to use only the dedicated Agent proxy for HTTP(S) traffic.
- Agent Squid ACLs allow private access only to `/agent-stub/` on `agentbackend` and `/files/` on `api`; other private destinations are denied by the proxy.
- Shell path isolation remains enabled.
- Documentation warns that Agent v2 must only be offered to trusted users, matching Dify's release warning.

This does not claim that proxy environment variables prevent arbitrary malicious code from opening direct sockets inside the shared ACA environment.

## Secrets

Terraform generates separate high-entropy values for:

- API-to-Agent-backend bearer authentication.
- Agent Stub JWE derivation.
- Shell-control authentication.

The values are stored in Azure Key Vault and injected consistently into the API, worker, Agent backend, and local sandbox. No development defaults are used. Sensitive outputs remain marked sensitive, following the project's existing secret pattern.

## Configuration Changes

The API and worker receive the Dify 1.16.1 Agent backend URL, bearer token, stream timeout, reconnect, and run-timeout variables. They also receive the 1.16.1 plugin-model-provider cache toggle.

The web container receives:

- `NEXT_PUBLIC_ENABLE_AGENT_V2` from `enable-dify-agent-v2`.
- `NEXT_PUBLIC_ENABLE_FEATURE_PREVIEW=true`, matching 1.16.1.
- `WORKFLOW_GENERATION_TIMEOUT_MS=180000`.

The API, worker, and worker-beat retain the existing Azure PostgreSQL, Azure Redis TLS, storage, pgvector, plugin, and event-bus configuration.

Existing timeout settings are compatibility requirements and must not be shortened or replaced during the upgrade:

- Plugin environment initialization: `PYTHON_ENV_INIT_TIMEOUT=120`.
- Plugin execution: `PLUGIN_MAX_EXECUTION_TIMEOUT=600`.
- Classic code sandbox worker: `WORKER_TIMEOUT=15`.
- File access: `FILES_ACCESS_TIMEOUT=300`.
- API-to-plugin daemon: `PLUGIN_DAEMON_TIMEOUT=600.0`.
- Web text generation: `TEXT_GENERATION_TIMEOUT_MS=60000`.
- Workflow execution limit: `WORKFLOW_MAX_EXECUTION_TIME=1200`.
- Access token lifetime: `ACCESS_TOKEN_EXPIRE_MINUTES=60`.
- Refresh token lifetime: `REFRESH_TOKEN_EXPIRE_DAYS=30`.
- SQLAlchemy connection recycle interval: `SQLALCHEMY_POOL_RECYCLE=3600`.

Dify 1.16.1's new Agent and workflow-generation timeout variables are additive: `AGENT_BACKEND_STREAM_READ_TIMEOUT_SECONDS=30`, `AGENT_BACKEND_RUN_TIMEOUT_SECONDS=1200`, and `WORKFLOW_GENERATION_TIMEOUT_MS=180000`.

Nginx gains `/openapi` and WebSocket forwarding while retaining API, files, plugin webhook, MCP, trigger, explore, and web routes.

The main SSRF proxy configuration is updated to Dify 1.16.1's split common/access-rule model, adapted to static Azure File Share files. A separate file share contains the Agent proxy configuration.

## Resource Organization

Existing classic services remain in `aca-env.tf`. New Agent resources live in `agent.tf` so the Agent security boundary, credentials, and service wiring can be reviewed independently. File-share resources stay in `fileshare.tf`; generated credentials stay in `secrets.tf` and `keyvault.tf`; image and feature variables stay in `var.tf`.

## Failure Handling and Deployment Ordering

Terraform dependencies ensure the proxy and local sandbox exist before the Agent backend, and the Agent backend exists before API/worker revisions use it. Each Agent service uses a single minimum replica. The local sandbox is kept at one maximum replica because its workspace is local and the official Compose architecture is singleton. Worker beat remains exactly one replica.

API startup continues to run Dify database migrations. Upgrade documentation will distinguish:

- Fresh installation: migrations run automatically; no 1.15 backfill is needed.
- Existing 1.15 installation: back up PostgreSQL and storage first; retain the documented plugin auto-upgrade backfill if it has not already been run.

## Validation Strategy

Configuration regression tests will be written before production edits. They will verify:

- Exact 1.16.1 image pins for API, web, Agent backend, and Agent local sandbox.
- Unchanged official 1.16.1 pins for plugin daemon and classic sandbox.
- Presence and internal-only ingress of all classic and Agent services.
- Singleton worker beat and local Agent sandbox.
- Correct shared-token wiring among API, worker, Agent backend, and local sandbox.
- Configurable `NEXT_PUBLIC_ENABLE_AGENT_V2` behavior.
- Agent v2 enabled by default and all pre-upgrade timeout values preserved exactly.
- Agent proxy ACLs and local-sandbox proxy variables.
- Nginx `/openapi`, WebSocket, plugin webhook, MCP, and trigger routes.
- Required PostgreSQL databases/extensions and persistent storage resources.
- Absence of Dify development Agent secrets.

Final verification will run the regression tests, `terraform fmt -check -recursive`, `terraform init -backend=false`, `terraform validate`, and a mocked/non-credentialed Terraform plan or Terraform test when supported by the available Terraform version. No Azure resources will be created during verification.

## Out of Scope

- Applying Terraform to an Azure subscription.
- Migrating live production data.
- Enabling public access to internal Agent services.
- Claiming Docker-equivalent network isolation within a single ACA environment.
- Enabling the optional collaboration WebSocket service; Nginx forwarding compatibility is retained for a future dedicated implementation.
